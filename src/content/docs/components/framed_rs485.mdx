The `framed_rs485` hub enables an ESPHome device to participate in DLE-framed
RS-485 buses. It receives and validates frames locally, allowing it to decode
them and expose the state of devices on the bus as Home Assistant entities
(e.g., pool water temperature). It also queues outbound commands so they
transmit precisely during the narrow timing window of the controller’s
keep-alive window (e.g., a Home Assistant button entity to turn on the pool
lights). Compared to performing these operations with a USB/TCP serial-based
app or an ESPHome Serial Proxy, these capabilities provide reliable command
delivery, low-latency feedback to observe the side effects of issued commands,
and significant event reduction by exposing Home Assistant to low-frequency
states instead of high-frequency frames.

Profiles bundle correct defaults for known controllers. Custom framing bytes,
CRC algorithms, TX gate behaviour, and user-supplied frame decoders (via
`on_frame:`) are all configurable in YAML, making the component useful beyond
any single product.

## Recommended framework: ESP-IDF

Use the **ESP-IDF framework**, not Arduino:

```yaml
esp32:
  board: esp32dev   # replace with your board identifier
  framework:
    type: esp-idf
```

When `flow_control_pin` is set on the `uart:` component under ESP-IDF, the
device's UART peripheral enters hardware RS-485 half-duplex mode
(`UART_MODE_RS485_HALF_DUPLEX`). The hardware asserts the DE/RE pin exactly when
the TX FIFO fills and deasserts only after the **shift register** finishes
clocking out the last bit — sub-bit precision that no software loop can match.

Under the Arduino framework the `uart:` component does **not** drive
`flow_control_pin`. Arduino users must therefore use an **auto-DE transceiver
chip** (e.g. MAX13487, MAX22025) where DE follows the TX line state
automatically. With auto-DE hardware, the `framed_rs485` TX path calls
`Serial::flush()` after each frame to keep the TX line active for the full
frame duration; on ESP-IDF the flush is omitted because the hardware mode
already handles deassertion timing.

`idle_gap` TX gate mode is sensitive to echo on the RX line — each transmitted
frame updates `last_rx_time_` via the echo, which resets the idle timer and may
prevent `idle_gap` from ever firing again. ESP-IDF's hardware RS-485 mode
suppresses TX echo automatically; on Arduino, prefer `frame_trigger` or
`fixed_delay`, or use a transceiver that suppresses local echo in hardware.

## Basic usage

Minimal Hayward AquaLogic configuration. User payload decoding is done via
`on_frame:` on the hub — one lambda per frame type, pushing values to
`platform: template` sensors. Hub diagnostics (frame counters, CRC failures,
queue depth) are exposed through the `framed_rs485` sensor and text_sensor
platforms.

```yaml
uart:
  id: pool_uart
  tx_pin: GPIO17
  rx_pin: GPIO18
  baud_rate: 19200
  data_bits: 8
  parity: NONE
  stop_bits: 2
  flow_control_pin: GPIO21  # DE/RE pin; omit if your adapter auto-manages direction

framed_rs485:
  id: pool
  uart_id: pool_uart
  profile: hayward_aqualogic_wireless

  on_frame:
    # LED status frame: decode the 32-bit mask once, push to all LED sensors.
    - frame_type: [0x01, 0x02]
      then:
        - lambda: |-
            if (payload.size() < 6) return;
            uint32_t mask = uint32_t(payload[2]) | (uint32_t(payload[3]) << 8) |
                            (uint32_t(payload[4]) << 16) | (uint32_t(payload[5]) << 24);
            id(led_filter).publish_state(bool(mask & (1UL << 5)));
            id(led_lights).publish_state(bool(mask & (1UL << 6)));

    # Display frame: decode the Hayward text encoding once, push to all display sensors.
    # A static (BSS) buffer avoids heap allocation during character extraction; one
    # std::string is constructed only at the publish_state call. Text sensors
    # deduplicate internally so repeated equal values are not forwarded to Home Assistant.
    - frame_type: [0x01, 0x03]
      then:
        - lambda: |-
            // BUF_LEN sized for Hayward Pro Logic's widest displays (~40 chars) plus
            // UTF-8 degree-symbol expansion. static: BSS-allocated once at program
            // start -- no per-call stack or heap, matching the hub's setup-time
            // buffer discipline.
            const size_t BUF_LEN = 128;
            static char out[BUF_LEN];
            uint8_t olen = 0;
            for (size_t i = 3; i < payload.size() && olen < (BUF_LEN - 2); i++) {
              uint8_t b = payload[i];
              if (b > 0x7F) b -= 0x80;
              if (b == 0) continue;
              if (b == '_') {
                if (olen + 2 <= (BUF_LEN - 2)) { out[olen++] = '\xC2'; out[olen++] = '\xB0'; }
              } else {
                out[olen++] = char(b);
              }
            }
            while (olen > 0 && out[olen - 1] == ' ') olen--;
            out[olen] = '\0';
            id(display_text).publish_state(std::string(out, olen));

binary_sensor:
  - platform: template
    id: led_filter
    name: "Filter LED"

  - platform: template
    id: led_lights
    name: "Lights LED"

text_sensor:
  - platform: template
    id: display_text
    name: "Display"

button:
  - platform: framed_rs485
    framed_rs485_id: pool
    name: "Filter"
    command: 0x80000000
```

## Writing `on_frame:` lambdas — best practices

`on_frame:` fires at bus frequency (~10 Hz for Hayward, faster on polled buses
like Jandy). To keep long-uptime devices stable, follow these patterns:

- **No heap allocation in the lambda.** Decode into fixed-size buffers
  (`char[BUF_LEN]`, `uint8_t[N]`, structs). Avoid `std::string text;` followed by
  `text.push_back()` — even with `reserve()`, the underlying string is freshly
  allocated each call. Build into a fixed buffer and construct one `std::string`
  only at the `publish_state(...)` call site.
- **Prefer `static` buffers for anything larger than a few bytes.** A `static`
  buffer inside a lambda is BSS-allocated once at program start (the same
  discipline the hub uses for its setup-time scratch buffers). Same memory
  story as the hub, no per-call stack pressure, no heap. Example:

  ```cpp
  const size_t BUF_LEN = 128;   // sized to cover the widest payload you expect
  static char text[BUF_LEN];    // allocated once in .bss; reused across calls
  uint8_t tlen = 0;             // local, resets each call
  // ... build into text[0..tlen) ...
  id(display_text).publish_state(std::string(text, tlen));
  ```

  Use a named constant (`BUF_LEN`) instead of bare magic numbers so the bound
  is obvious and easy to bump if your display turns out wider than expected.
  ESPHome lambdas run on the single-threaded main loop, so static reuse is
  race-free.
- **Guard payload lengths.** Always `if (payload.size() < N) return;` before
  indexing past the frame type. A short or malformed frame would otherwise
  read past the vector end.
- **Avoid `std::to_string`, `String::format`, and other allocating helpers**
  inside the lambda. Use `snprintf` into a `static char[]` buffer if you need
  formatted text.
- **Don't block.** A long loop or `delay()` inside the lambda stalls every
  other ESPHome component for the duration. Keep decode logic tight.

For broader background, see [ESPHome Lambda Magic](/automations/templates.md#lambda-magic).

## Hardware setup

Use an RS-485-to-TTL adapter connected to a UART on your ESPHome device, or
an integrated device like WaveShare's ESP32-S3-RS485-CAN which has both the
RS-485-to-TTL and an ESP32-S3. See the [UART](/components/uart/) component
for wiring details.

```
GPIO17 (TX) → DI  (adapter data-in)
GPIO18 (RX) → RO  (adapter data-out)
GPIO21      → DE + RE tied (half-duplex direction control)
DC Supply   → VCC (match adapter supply voltage)
GND         → GND
A / B       → RS-485 bus terminals
```

For half-duplex adapters with a DE/RE pin, set `flow_control_pin` on the
**`uart:` component** (not on `framed_rs485:`). Under ESP-IDF this activates
the UART peripheral's built-in RS-485 half-duplex mode; the hardware drives
DE with shift-register-level precision and suppresses the TX echo on RX
automatically.

```yaml
uart:
  flow_control_pin: GPIO21  # DE/RE direction pin
```

If you receive no data, try swapping `tx_pin`/`rx_pin` or the A/B bus wires.
Some adapters label DI/RO from the adapter's perspective, which is the reverse
of the device's.

## Profiles

Profiles set correct UART settings, gate frame defaults, and key-frame format
automatically. The profile is the device we are attempting to mimic.

| Profile | UART | CRC | Key format | Default gate frame |
|---|---|---|---|---|
| `hayward_aqualogic_wireless` *(default)* | 19200 8N2 | sum16 header-inclusive | wireless 12-byte | `[0x01, 0x01]` (keep-alive) |
| `hayward_aqualogic_wired_remote` | 19200 8N2 | sum16 payload-only | wired remote | `[0x01, 0x01]` |
| `hayward_aqualogic_wired_local` | 19200 8N2 | sum16 payload-only | wired local | `[0x01, 0x01]` |
| `jandy_aqualink_rs` | 9600 8N1 | sum8 header-inclusive | jandy_allbutton | `[0x08, 0x00]` (AllButton probe) |
| `generic_framed_rs485` | any | manual | manual | `[0x01, 0x01]` |

Hayward and Jandy profiles enforce UART settings at config-validation time.
Use `generic_framed_rs485` to bypass validation for custom buses.

`jandy_aqualink_rs` additionally requires `tx.idle_command` (typically `0x00`)
unless `sniffer_only: true`. The AllButton emulator must ACK every probe
within the Jandy poll cycle or the controller will mark it offline.

## Configuration variables

- **id** (*Optional*, [ID](/guides/configuration-types#id)): Manually specify the ID of the hub.
- **uart_id** (**Required**, [ID](/guides/configuration-types#id)): The ID of the [UART](/components/uart/) bus.
- **profile** (*Optional*, string): One of the profile names above. Defaults to `hayward_aqualogic_wireless`.
- **sniffer_only** (*Optional*, boolean): Disable all TX including buttons. Defaults to `false`.
- **dump_frames** (*Optional*, boolean): Log every validated RX frame payload and every TX frame at DEBUG level. Defaults to `false`.
- **max_frame_length** (*Optional*, integer, 6–1024): Discard frames longer than this many bytes. Defaults to `128`.
- **frame_timeout** (*Optional*, [Time](/guides/configuration-types#time)): Reset receive state if a partial frame sits on the bus longer than this. Prevents a noise burst or mid-frame cable pull from permanently stalling reception. Defaults to `50ms`.
- **framing** (*Optional*): Override DLE-framing delimiter bytes. Rarely needed.

  - **dle** (*Optional*, hex byte): Frame delimiter byte. Defaults to `0x10`.
  - **stx** (*Optional*, hex byte): Start-of-frame byte. Defaults to `0x02`.
  - **etx** (*Optional*, hex byte): End-of-frame byte. Defaults to `0x03`.
  - **escape_byte** (*Optional*, hex byte): Escape suffix for DLE bytes in payload. Defaults to `0x00`.

- **crc** (*Optional*): CRC algorithm configuration.

  - **type** (*Optional*, string): `none`, `sum8`, `sum16`, `xor8`, or `crc16_modbus`. Defaults to `sum16`.
  - **rx_accept** (*Optional*, list): CRC variants accepted on RX — `header_inclusive`, `payload_only`, or both. Defaults to both.
  - **tx_variant** (*Optional*, string): CRC variant used when building outbound frames. Set by profile.

  `header_inclusive` includes DLE+STX in the CRC sum (Hayward wireless).
  `payload_only` computes the CRC over the unescaped payload only (Hayward wired remotes).

- **key_format** (*Optional*, string): Button command encoding. Set automatically by the active
  profile; only needed when using `generic_framed_rs485` with buttons.

  | Value | Used by |
  |---|---|
  | `wireless_12byte` *(default for generic)* | Hayward AquaLogic wireless remote (frame type `0x0083`, 12-byte payload: 3-byte header + 4-byte key × 2 + 1 pad) |
  | `wired_remote` | Hayward AquaLogic wired remote |
  | `wired_local` | Hayward AquaLogic local wired controller |
  | `jandy_allbutton` | Jandy AquaLink RS AllButton frame |

- **on_frame** (*Optional*, [Automation](/guides/automations)): Automation(s) that fire when a
  matching frame is received. Multiple entries may be listed; each fires independently based
  on its `frame_type` filter. The automation receives the payload as `payload`
  (`const std::vector<uint8_t> &`). Use `[]` to match every frame.

  - **frame_type** (**Required**, list of hex bytes): Frame-type prefix to match against the start of each
    received payload. Use `[]` to match every frame. Conventionally one or two bytes; up to eight bytes
    are accepted (enforced at config time). See the lambda best-practices section above.

- **tx** (*Optional*): TX and command-queue configuration.

  - **queue_policy** (*Optional*, string): `replace_latest` (new command overwrites pending) or `fifo`. Defaults to `replace_latest`.
  - **max_queue_size** (*Optional*, integer, 1–32): Maximum commands in queue. Must be `1` for `replace_latest`. Defaults to `1`.
  - **idle_command** (*Optional*, hex uint32): Command value to send on the gate trigger when no real command is queued.
    **Required for `jandy_aqualink_rs`** unless `sniffer_only` is true — the AllButton emulator must ACK every probe.
    The encoding follows `key_format`: for `wireless_12byte` the full 32 bits are used; for `jandy_allbutton` only the
    low byte is used as the button code. See `button.command` for the same encoding rules. Idle transmissions are not
    counted in the `commands_sent` diagnostic.

  - **gate** (*Optional*): TX gate — controls when queued commands are transmitted.

    - **mode** (*Optional*, string): `frame_trigger` (default), `idle_gap`, or `fixed_delay`.
    - **frame_type** (*Optional*, list of hex bytes): Gate frame for `frame_trigger` mode. Defaults to the profile-appropriate keep-alive (see profile table above). Required and must be non-empty when `mode` is `frame_trigger` and `sniffer_only` is false; a configuration that would never fire is rejected at config time.
    - **delay** (*Optional*, [Time](/guides/configuration-types#time)): Additional delay after the gate frame fires. Defaults to `0ms`.
    - **min_silence** (*Optional*, [Time](/guides/configuration-types#time)): Bus silence required for `idle_gap` mode. Defaults to `4ms`.
    - **interval** (*Optional*, [Time](/guides/configuration-types#time)): TX interval for `fixed_delay` mode. Defaults to `100ms`.

## Payload layout

All `on_frame:` handlers receive the same payload byte vector:

```
Bytes 0..N-1   frame_type prefix bytes (N = length of the configured frame_type)
Bytes N+      frame data
              CRC bytes are stripped during validation
```

For most protocols `N` is 2, but the schema accepts up to 8. Always guard
against short payloads in lambdas before indexing past the prefix:

```yaml
lambda: |-
  if (payload.size() < 5) return;
  // payload[2..] is frame data for a 2-byte frame_type
```

### Offset convention: payload-relative

`framed_rs485` uses **payload-relative** byte offsets: `payload[0]` is the
first byte of the `frame_type` prefix. For the typical 2-byte frame_type, the
first data byte is at `payload[2]`. This matches what the lambda actually
receives at the C++ level — the `payload` vector has already had the DLE+STX
preamble stripped, escapes unwrapped, and CRC removed, but the frame_type
bytes are still at the start.

**Community references often use a different convention.** Some strip the
frame_type before counting, so what they call "byte 0" of the frame is our
`payload[2]`. When porting offsets from external research, add the
`frame_type` length (usually 2) to translate.

| Source | Their "byte 0" of the frame | Equivalent in our `payload[]` |
|---|---|---|
| **`framed_rs485`** (this component) | first byte of the frame_type | `payload[0]` |
| [swilson/aqualogic](https://github.com/swilson/aqualogic) | first byte **after** the frame_type | `payload[2]` (for 2-byte frame_type) |
| [earlephilhower/aquaweb](https://github.com/earlephilhower/aquaweb) | mixed; see the Python source for each frame | translate per-field |
| Raw bus capture (Wireshark, dump_frames log) | `DLE` itself | DLE+STX are stripped before `payload[0]` |

When publishing your own reverse-engineering findings, state the convention
explicitly ("offsets are payload-relative: `payload[0..1]` = frame_type, data
starts at `payload[2]`") — it costs one sentence and saves every reader an
off-by-two debugging session.

## Getting started with an unknown bus

Use this workflow for controllers not covered by a built-in profile.

### Step 1: Gather existing research

Search for prior work before touching hardware. The HA community forums and GitHub
often have threads with baud rates, framing details, and frame-type catalogs for
specific controllers.

### Step 2: Flash a passive sniffer

Create a YAML with `sniffer_only: true`, `dump_frames: true`, and
`profile: generic_framed_rs485`. Set `crc: {type: none}` so every framing-valid
frame is logged regardless of CRC.

```yaml
framed_rs485:
  id: bus
  uart_id: bus_uart
  profile: generic_framed_rs485
  sniffer_only: true
  dump_frames: true
  crc:
    type: none

text_sensor:
  - platform: framed_rs485
    framed_rs485_id: bus
    name: "Last Frame Type"

sensor:
  - platform: framed_rs485
    framed_rs485_id: bus
    name: "Frames Received"
    decode: frames_received
    filters:
      - throttle: 10s
```

### Step 3: Catalog frame types from logs

With `dump_frames: true` and logger at DEBUG level, each validated frame is logged:

```
[D][framed_rs485:xxx]: RX 010101
[D][framed_rs485:xxx]: RX 0102010200000800000800
[D][framed_rs485:xxx]: RX 010301035000506f6f6c2054...
```

The first four hex chars are the two-byte frame type. Collect these over a few
minutes and note cadence. Press physical buttons and watch for new frame types.

### Step 4: Confirm the CRC

Once you have captured payloads, test CRC candidates. Temporarily set `rx_accept`
to only one variant and watch whether `crc_failures` climbs.

### Step 5: Configure decoders

Replace the sniffer config with `on_frame:` handlers that decode each frame type
of interest, plus `template` sensors that receive the decoded values via
`id(...).publish_state(...)`. See the [Basic usage](#basic-usage) example.

## Diagnostics

The `framed_rs485` sensor and text_sensor platforms expose hub-state diagnostics
as Home Assistant entities. They do **not** decode user payloads — for that, use
`on_frame:`.

| sensor `decode` | Description |
|---|---|
| `frames_received` | Running count of validated frames received |
| `crc_failures` | Running count of frames that failed validation (CRC or structural) |
| `commands_sent` | Running count of user commands transmitted (idle keepalives are not counted) |
| `command_drops` | Running count of commands dropped (queue full or sniffer mode) |
| `last_keepalive_ms` | Measured interval between the two most recent gate frames, in ms |
| `queue_depth` | Current TX queue depth (including any pending delayed frame) |

The text_sensor exposes one diagnostic: the most recent validated frame type as a
4-character hex string (e.g. `"0083"`, no separator). It publishes only on change.

```yaml
sensor:
  - platform: framed_rs485
    framed_rs485_id: pool
    name: "Frames Received"
    decode: frames_received

  - platform: framed_rs485
    framed_rs485_id: pool
    name: "CRC Failures"
    decode: crc_failures

text_sensor:
  - platform: framed_rs485
    framed_rs485_id: pool
    name: "Last Frame Type"
```

A rising `crc_failures` with zero `frames_received` usually means the wrong baud
rate or UART settings. A small steady `crc_failures` alongside healthy
`frames_received` suggests `crc.type` or `crc.rx_accept` needs adjustment.

## Why buttons, not switches

Commands are **buttons** because they are keypress events on the RS-485 bus — the
controller decides the resulting state. Read LED state through Home Assistant
binary sensors driven by your `on_frame:` LED-mask handler for the ground truth
on what is on or off.
