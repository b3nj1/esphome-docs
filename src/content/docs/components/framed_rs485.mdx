The `framed_rs485` hub lets an ESP32 participate in DLE-framed RS-485 buses.
It validates frames locally, exposes Home Assistant entities through ESPHome, and
queues outbound commands so they transmit during the controller's keep-alive window.

Profiles bundle correct defaults for known controllers. Custom framing bytes, CRC
algorithms, TX gate behaviour, built-in decoders, and user lambdas are all
configurable in YAML, making the component useful beyond any single product.

## Recommended framework: ESP-IDF

Use the **ESP-IDF framework**, not Arduino:

```yaml
esp32:
  board: esp32dev   # replace with your board identifier
  framework:
    type: esp-idf
```

When `flow_control_pin` is set on the `uart:` component under ESP-IDF, the ESP32
UART peripheral enters hardware RS-485 half-duplex mode
(`UART_MODE_RS485_HALF_DUPLEX`). The hardware asserts the DE/RE pin exactly when
the TX FIFO fills and deasserts only after the **shift register** finishes clocking
out the last bit — sub-bit precision that no software loop can match.

Under the Arduino framework the UART component falls back to software pin toggling
around `write()` calls: DE deasserts as soon as the FIFO drains, while the final
byte is still shifting. This can clip the last bit on the bus, causing intermittent
CRC failures or missed commands. Arduino also has no hardware RS-485 echo
suppression, so the hub may read its own transmitted bytes as incoming frames.

`idle_gap` TX gate mode is particularly affected under Arduino: each transmitted
frame updates `last_rx_time_` via the echo, which resets the idle timer and may
prevent `idle_gap` from ever firing again. Use `frame_trigger` or `fixed_delay`
under Arduino, or switch to ESP-IDF.

## Basic usage

Minimal Hayward AquaLogic configuration (read sensors and send button commands).

When multiple sensors share the same frame type, use `on_frame:` on the hub to decode
the payload once and push values to `template` sensors — one lambda, all sensors updated:

```yaml
esp32:
  board: esp32dev
  framework:
    type: esp-idf

uart:
  id: pool_uart
  tx_pin: GPIO17
  rx_pin: GPIO16
  baud_rate: 19200
  data_bits: 8
  parity: NONE
  stop_bits: 2
  flow_control_pin: GPIO4   # DE/RE pin; omit if your adapter auto-manages direction

framed_rs485:
  id: pool
  uart_id: pool_uart
  profile: hayward_aqualogic_wireless

  on_frame:
    # LED status frame: decode the 32-bit mask once, push to all LED sensors.
    - frame_type: [0x01, 0x02]
      then:
        - lambda: |-
            if (payload.size() < 6) return;
            uint32_t mask = uint32_t(payload[2]) | (uint32_t(payload[3]) << 8) |
                            (uint32_t(payload[4]) << 16) | (uint32_t(payload[5]) << 24);
            id(led_filter).publish_state(bool(mask & (1UL << 5)));
            id(led_lights).publish_state(bool(mask & (1UL << 6)));

    # Display frame: decode the Hayward text encoding once, push to all display sensors.
    # Stack buffer avoids heap allocation during character extraction; one std::string
    # is constructed only at the publish_state call. Text sensors deduplicate internally
    # so repeated equal values are not forwarded to Home Assistant.
    - frame_type: [0x01, 0x03]
      then:
        - lambda: |-
            char out[32] = {};
            uint8_t olen = 0;
            for (size_t i = 3; i < payload.size() && olen < 30; i++) {
              uint8_t b = payload[i];
              if (b > 0x7F) b -= 0x80;
              if (b == 0) continue;
              if (b == '_') {
                if (olen + 2 <= 30) { out[olen++] = '\xC2'; out[olen++] = '\xB0'; }
              } else {
                out[olen++] = char(b);
              }
            }
            while (olen > 0 && out[olen - 1] == ' ') olen--;
            out[olen] = '\0';
            id(display_text).publish_state(std::string(out, olen));

binary_sensor:
  - platform: template
    id: led_filter
    name: "Filter LED"

  - platform: template
    id: led_lights
    name: "Lights LED"

text_sensor:
  - platform: template
    id: display_text
    name: "Display"

button:
  - platform: framed_rs485
    framed_rs485_id: pool
    name: "Filter"
    command: 0x80000000
```

## Hardware setup

Use an RS-485-to-TTL adapter connected to an ESP32 UART. See the [UART](/components/uart/) component for wiring details.

```
ESP32 GPIO17 (TX) → DI  (adapter data-in)
ESP32 GPIO16 (RX) → RO  (adapter data-out)
ESP32 GPIO4       → DE + RE tied (half-duplex direction control)
3.3 V or 5 V      → VCC (match adapter supply voltage)
GND               → GND
A / B             → RS-485 bus terminals
```

For half-duplex adapters with a DE/RE pin, set `flow_control_pin` on the **`uart:`
component** (not on `framed_rs485:`). Under ESP-IDF this activates the UART
peripheral's built-in RS-485 half-duplex mode; the hardware drives DE with
shift-register-level precision and suppresses the TX echo on RX automatically.

```yaml
uart:
  flow_control_pin: GPIO4   # DE/RE direction pin
```

If you receive no data, try swapping `tx_pin`/`rx_pin` or the A/B bus wires.
Some adapters label DI/RO from the adapter's perspective, which is the reverse of
the ESP32's.

## Profiles

Profiles set correct UART settings and key-frame format automatically.

| Profile | UART | CRC | Key format |
|---|---|---|---|
| `hayward_aqualogic_wireless` *(default)* | 19200 8N2 | sum16 header-inclusive | wireless 9-byte |
| `hayward_aqualogic_wired_remote` | 19200 8N2 | sum16 payload-only | wired remote |
| `hayward_aqualogic_wired_local` | 19200 8N2 | sum16 payload-only | wired local |
| `jandy_aqualink_rs` | 9600 8N1 | sum8 header-inclusive | jandy_allbutton |
| `generic_framed_rs485` | any | manual | manual |

Hayward and Jandy profiles enforce UART settings at config-validation time.
Use `generic_framed_rs485` to bypass validation for custom buses.

## Configuration variables

- **id** (*Optional*, [ID](/guides/configuration-types#id)): Manually specify the ID of the hub.
- **uart_id** (**Required**, [ID](/guides/configuration-types#id)): The ID of the [UART](/components/uart/) bus.
- **profile** (*Optional*, string): One of the profile names above. Defaults to `hayward_aqualogic_wireless`.
- **sniffer_only** (*Optional*, boolean): Disable all TX including buttons. Defaults to `false`.
- **dump_frames** (*Optional*, boolean): Log every validated frame payload at DEBUG level. Defaults to `false`.
- **max_frame_length** (*Optional*, integer): Discard frames longer than this many bytes. Defaults to `128`.
- **frame_timeout** (*Optional*, [Time](/guides/configuration-types#time)): Reset receive state if a partial frame sits on the bus longer than this. Prevents a noise burst or mid-frame cable pull from permanently stalling reception. Defaults to `50ms`.
- **framing** (*Optional*): Override DLE-framing delimiter bytes. Rarely needed.

  - **dle** (*Optional*, hex byte): Frame delimiter byte. Defaults to `0x10`.
  - **stx** (*Optional*, hex byte): Start-of-frame byte. Defaults to `0x02`.
  - **etx** (*Optional*, hex byte): End-of-frame byte. Defaults to `0x03`.
  - **escape_byte** (*Optional*, hex byte): Escape suffix for DLE bytes in payload. Defaults to `0x00`.

- **crc** (*Optional*): CRC algorithm configuration.

  - **type** (*Optional*, string): `none`, `sum8`, `sum16`, `xor8`, or `crc16_modbus`. Defaults to `sum16`.
  - **rx_accept** (*Optional*, list): CRC variants accepted on RX — `header_inclusive`, `payload_only`, or both. Defaults to both.
  - **tx_variant** (*Optional*, string): CRC variant used when building outbound frames. Set by profile.

  `header_inclusive` includes DLE+STX in the CRC sum (Hayward wireless).
  `payload_only` computes the CRC over the unescaped payload only (Hayward wired remotes).

- **key_format** (*Optional*, string): Button command encoding. Set automatically by the active
  profile; only needed when using `generic_framed_rs485` with buttons.

  | Value | Used by |
  |---|---|
  | `wireless_9byte` *(default for generic)* | Hayward AquaLogic wireless remote (frame type `0x0083`, 9-byte payload) |
  | `wired_remote` | Hayward AquaLogic wired remote |
  | `wired_local` | Hayward AquaLogic local wired controller |
  | `jandy_allbutton` | Jandy AquaLink RS AllButton frame |

- **on_frame** (*Optional*, [Automation](/guides/automations)): Automation(s) that fire when a
  matching frame is received. Multiple entries may be listed; each fires independently based
  on its `frame_type` filter. The automation receives the payload as `payload`
  (`const std::vector<uint8_t> &`). Use `[]` to match every frame.

  - **frame_type** (**Required**, list of hex bytes): Frame-type prefix to match against the start of each
    received payload. Use `[]` to match every frame. Conventionally one or two bytes; up to eight bytes
    are accepted by the schema.

  `on_frame` is the primary way to write a single decode lambda that updates multiple sensors
  at once. Template sensors (`platform: template`) receive values via `id(sensor_id).publish_state(...)`.
  See the [Hayward AquaLogic example](#basic-usage) for the LED-mask and display-text patterns.

  **Allocation:** LED-mask frames are fully allocation-free — decode into local integer variables and
  call `publish_state`. Display-text frames require one `std::string` construction per
  `publish_state` call; use a `char[]` stack buffer for intermediate decoding and only
  construct the `std::string` at the call site. Binary and text sensors deduplicate
  internally: repeated `publish_state` calls with the same value do not forward updates to
  Home Assistant. Numeric sensors do not deduplicate — use `filters: throttle:` or
  `filters: delta:` to avoid unnecessary network traffic at bus frequency.

- **tx** (*Optional*): TX and command-queue configuration.

  - **queue_policy** (*Optional*, string): `replace_latest` (new command overwrites pending) or `fifo`. Defaults to `replace_latest`.
  - **max_queue_size** (*Optional*, integer): Maximum commands in queue. Must be `1` for `replace_latest`. Defaults to `1`.
  - **idle_command** (*Optional*, hex uint32): Command value to send on the gate trigger when no real command is queued.
    Required for Jandy AllButton emulation. The encoding follows `key_format`: for `wireless_9byte` the full 32 bits
    are used; for `jandy_allbutton` only the low byte is used as the button code. See `button.command` for the same
    encoding rules. Idle transmissions are not counted in the `commands_sent` diagnostic.

  - **gate** (*Optional*): TX gate — controls when queued commands are transmitted.

    - **mode** (*Optional*, string): `frame_trigger` (default), `idle_gap`, or `fixed_delay`.
    - **frame_type** (*Optional*, list of hex bytes): Gate frame for `frame_trigger` mode. Defaults to `[0x01, 0x01]` (Hayward keep-alive).
    - **delay** (*Optional*, [Time](/guides/configuration-types#time)): Additional delay after the gate frame fires. Defaults to `0ms`.
    - **min_silence** (*Optional*, [Time](/guides/configuration-types#time)): Bus silence required for `idle_gap` mode. Defaults to `4ms`.
    - **interval** (*Optional*, [Time](/guides/configuration-types#time)): TX interval for `fixed_delay` mode. Defaults to `100ms`.

## Payload layout

All listeners receive the same payload byte vector:

```
Bytes 0–1    two-byte frame type (matches frame_type: [...] filter)
Bytes 2+     frame data
             CRC bytes are stripped during validation
```

Always guard against short payloads in lambdas before indexing:

```yaml
lambda: |-
  if (payload.size() < 5) return {};
  return float(payload[4]);
```

## Getting started with an unknown bus

Use this workflow for controllers not covered by a built-in profile.

### Step 1: Gather existing research

Search for prior work before touching hardware. The HA community forums and GitHub
often have threads with baud rates, framing details, and frame-type catalogs for
specific controllers.

### Step 2: Flash a passive sniffer

Create a YAML with `sniffer_only: true`, `dump_frames: true`, and
`profile: generic_framed_rs485`. Set `crc: {type: none}` so every framing-valid
frame is logged regardless of CRC.

```yaml
framed_rs485:
  id: bus
  uart_id: bus_uart
  profile: generic_framed_rs485
  sniffer_only: true
  dump_frames: true
  crc:
    type: none

text_sensor:
  - platform: framed_rs485
    framed_rs485_id: bus
    name: "Last Frame Type"
    frame_type: []

sensor:
  - platform: framed_rs485
    framed_rs485_id: bus
    name: "Frames Received"
    frame_type: []
    decode: frames_received
    state_class: total_increasing
    filters:
      - throttle: 10s
```

### Step 3: Catalog frame types from logs

With `dump_frames: true` and logger at DEBUG level, each validated frame is logged:

```
[D][framed_rs485:xxx]: RX 010101
[D][framed_rs485:xxx]: RX 0102010200000800000800
[D][framed_rs485:xxx]: RX 010301035000506f6f6c2054...
```

The first four hex chars are the two-byte frame type. Collect these over a few
minutes and note cadence. Press physical buttons and watch for new frame types.

### Step 4: Confirm the CRC

Once you have captured payloads, test CRC candidates. Temporarily set `rx_accept`
to only one variant and watch whether `crc_failures` climbs.

### Step 5: Configure decoders

Replace the sniffer config with sensor and button definitions. Use `on_frame:` on the
hub when multiple sensors share the same frame type (decode once, push to all). Use
`decode:` or per-sensor `lambda:` when a sensor is the sole reader of its frame type.

## Diagnostics

```yaml
framed_rs485:
  id: pool
  uart_id: pool_uart
  profile: hayward_aqualogic_wireless
  dump_frames: true
  sniffer_only: true
```

Sensor decode types for diagnostics (work with any `frame_type:` including `[]`):

| decode | Description |
|---|---|
| `frames_received` | Running count of validated frames received |
| `crc_failures` | Running count of frames that failed CRC |
| `commands_sent` | Running count of TX frames sent |
| `command_drops` | Running count of commands dropped (queue full or sniffer mode) |
| `last_keepalive_ms` | Measured interval between the two most recent gate frames, in ms |
| `queue_depth` | Current TX queue depth |

A rising `crc_failures` with zero `frames_received` usually means the wrong baud
rate or UART settings. A small steady `crc_failures` alongside healthy
`frames_received` suggests `crc.type` or `crc.rx_accept` needs adjustment.

## Why buttons, not switches

Commands are **buttons** because they are keypress events on the RS-485 bus — the
controller decides the resulting state. Read LED state through **binary sensors**
for the ground truth on what is on or off.
