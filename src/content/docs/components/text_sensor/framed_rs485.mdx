The `framed_rs485` text_sensor platform exposes a single hub diagnostic: the
type of the most recently validated frame, as a 4-character hex string (e.g.
`"0083"`, no separator). It requires the [Framed RS-485](/components/framed_rs485/)
hub to be configured.

This is useful for catalogueing frame types on an unknown bus during the
discovery workflow. For user payload decoding, use [`on_frame:` on the
hub](/components/framed_rs485/#configuration-variables) — that handles every
text-decoding case from a single ASCII frame through Hayward AquaLogic's
blink-bit-and-degree-symbol display encoding.

## Configuration variables

- **framed_rs485_id** (**Required**, [ID](/guides/configuration-types#id)): The ID of the `framed_rs485` hub.

All other options from [Text Sensor](/components/text_sensor/#base-text-sensor-configuration).

The sensor publishes only on change — a steady-state bus produces no API traffic.

## Example

```yaml
text_sensor:
  - platform: framed_rs485
    framed_rs485_id: pool
    name: "Last Frame Type"
```

When a frame with payload starting `0x01 0x03 ...` is validated, the sensor
publishes the state `"0103"`. The first two payload bytes are shown; longer
frame_type prefixes still match in your `on_frame:` handlers but the diagnostic
shows only the leading two bytes (which is the conventional frame type width).
