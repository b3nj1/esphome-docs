The `framed_rs485` sensor platform exposes hub-state diagnostics (frame counters,
CRC failures, queue depth, etc.) as Home Assistant sensors. It requires the
[Framed RS-485](/components/framed_rs485/) hub to be configured.

User payload decoding is **not** done on this platform. To decode the contents
of received frames, use [`on_frame:` on the hub](/components/framed_rs485/#configuration-variables)
with `platform: template` sensors — that pattern handles every case from a
single bit-field LED mask through a multi-field temperature/text frame.

## Configuration variables

- **framed_rs485_id** (**Required**, [ID](/guides/configuration-types#id)): The ID of the `framed_rs485` hub.
- **decode** (**Required**, string): Which hub diagnostic value to publish.

  | decode | Description |
  |---|---|
  | `frames_received` | Running count of validated frames received. |
  | `crc_failures` | Running count of frames that failed validation (CRC mismatch or structural). |
  | `commands_sent` | Running count of user commands transmitted (idle keepalives are not counted). |
  | `command_drops` | Running count of commands dropped (queue full or sniffer mode). |
  | `last_keepalive_ms` | Measured interval between the two most recent gate frames, in ms. |
  | `queue_depth` | Current TX queue depth (including any pending delayed frame). |

All other options from [Sensor](/components/sensor/#base-sensor-configuration).

Sensors publish on change only. A counter that has not advanced does not generate
API traffic, so no `throttle` filter is required for steady-state operation.

## Example

```yaml
sensor:
  - platform: framed_rs485
    framed_rs485_id: pool
    name: "Frames Received"
    decode: frames_received

  - platform: framed_rs485
    framed_rs485_id: pool
    name: "CRC Failures"
    decode: crc_failures

  - platform: framed_rs485
    framed_rs485_id: pool
    name: "Queue Depth"
    decode: queue_depth
```

## Interpreting the counters

- A rising `crc_failures` with zero `frames_received` usually means the wrong
  baud rate or UART settings.
- A small steady `crc_failures` alongside healthy `frames_received` suggests
  `crc.type` or `crc.rx_accept` needs adjustment.
- `command_drops` should stay at 0 in normal operation. With `queue_policy: replace_latest`,
  every press that arrives while another command is pending increments the counter — useful for
  detecting button mash. With `queue_policy: fifo`, drops indicate the queue is too small.
- `last_keepalive_ms` shows the bus poll interval. Sudden changes here often
  indicate bus contention or controller reboots.
