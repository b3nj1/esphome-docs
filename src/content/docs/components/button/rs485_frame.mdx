The `rs485_frame` button platform sends a frame onto a DLE-framed RS485 bus when
pressed. It requires the [RS485 Frame](/components/rs485_frame/) hub to be configured,
and supports two construction forms:

- **`command:`** — encodes a 32-bit key value into the on-wire payload using the hub's
  [`command_format:`](/components/rs485_frame/#command_format) block. Requires the hub to have
  a `command_format:` set. Note that `command_format.command_size` may serialise only the low
  1 or 2 bytes of the value (see the hub's `command_format` docs).
- **`frame_type:` + `payload:`** — bypasses `command_format:` entirely. The supplied
  frame type and payload bytes are sent as-is after DLE-framing, byte-stuffing, and CRC.
  Use this for hubs with no `command_format:`, probe frames, or any custom frame layout. See
  also the [rs485_frame.send_frame action](/components/rs485_frame/#raw-frame-transmission)
  for invoking raw frames from scripts or computed-payload contexts.

The two forms are mutually exclusive on the same button.

## How commands work

A button press queues a frame on the hub, which transmits it during the next TX gate
window (typically the controller's keep-alive frame, around every 100 ms for Hayward
AquaLogic). The controller decides what happens next; the device cannot know the
outcome until it reads the next LED status frame. That is why commands are modelled as
buttons rather than switches.

### Finding command values

Known `command:` values for Hayward AquaLogic and Jandy AquaLink RS are listed in the
[rs485_frame-examples](https://github.com/b3nj1/rs485_frame-examples) repository and
were confirmed from live bus captures. AUX outputs are controller-wiring-dependent —
rename and verify against your physical panel.

To find new command values, enable `dump_frames: true` and `sniffer_only: true` on
the hub, press a physical button on the controller panel, and watch for a new frame
type (typically `0x0083` for Hayward wireless) in the ESP log. For an unknown protocol,
capture the full frame from a vendor controller and use the raw form below — or describe
the frame structure with `command_format:` on the hub if it fits the preamble / command
bytes / postamble shape.

## Configuration variables

- **rs485_frame_id** (**Required**, [ID](/guides/configuration-types#id)): The ID of the `rs485_frame` hub.

Provide **exactly one** of the following two forms:

- **command** (**Required**, hex uint32): Command value (e.g. `0x00010000`). Encoded by the
  hub's `command_format:`, which may use only the low 1 or 2 bytes depending on
  `command_size`. Rejected at config time if the hub has no `command_format:` — use the raw
  form instead, or add `command_format:` to the hub.
- **frame_type** + **payload** (**Required together** when not using `command:`):

  - **frame_type** (list of hex bytes): 2-byte (or longer, up to 8 bytes) frame type prefix.
    Same convention as `gate.frame_type` and `on_frame.frame_type` elsewhere in the component.
  - **payload** (list of hex bytes): The payload bytes that follow the frame type.
    Caller-composed; the hub adds framing and CRC.

All other options from [Button](/components/button/#base-button-configuration).

## Examples

### Command form (hub with a `command_format:`)

```yaml
button:
  - platform: rs485_frame
    rs485_frame_id: pool
    name: "Pool Lights"
    command: 0x00010000  # confirmed from bus capture

  - platform: rs485_frame
    rs485_frame_id: pool
    name: "Filter"
    command: 0x80000000

  - platform: rs485_frame
    rs485_frame_id: pool
    name: "Pool/Spa Mode"
    command: 0x40000000
```

### Raw form (custom devices, no `command_format:`)

```yaml
button:
  - platform: rs485_frame
    rs485_frame_id: my_device
    name: "Open Door"
    frame_type: [0x00, 0xA1]
    payload: [0x01, 0x00, 0x55]

  - platform: rs485_frame
    rs485_frame_id: my_device
    name: "Close Door"
    frame_type: [0x00, 0xA1]
    payload: [0x01, 0x00, 0xAA]
```

Use the corresponding LED binary sensors to read the actual resulting state.
LED state lives in a status frame from the controller; decode it in `on_frame:`
on the hub and push to `template` sensors — see the
[Basic usage example](/components/rs485_frame/#basic-usage) for the LED-mask
pattern. For a single LED:

```yaml
rs485_frame:
  id: pool
  on_frame:
    - frame_type: [0x01, 0x02]
      then:
        - lambda: |-
            if (payload.size() < 6) return;
            uint32_t mask = uint32_t(payload[2]) | (uint32_t(payload[3]) << 8) |
                            (uint32_t(payload[4]) << 16) | (uint32_t(payload[5]) << 24);
            id(led_filter).publish_state(bool(mask & (1UL << 5)));

binary_sensor:
  - platform: template
    id: led_filter
    name: "Filter"
```
